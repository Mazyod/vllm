## Configuration decisions

The [engine YAML tested by this gate](https://github.com/Mazyod/vllm/blob/40467091e0c99ff541b48ea9ee2f1891d09acf55/fork/bench/configs/v0.34.0/engine/deepseek-v41-tp4.yaml) retains only pinned identity,
TP4, API parsers/automatic tools, data-parallel vision, DSpark sampling, and the
scheduler setting needed for memory fit.

The current engine file subsequently adds `enable-prompt-tokens-details: true`.
That API metadata change was checked on CPU with the released image's parser
and response serialization; this hardware gate was not rerun for it.

| setting | evidence |
| --- | --- |
| `max-num-seqs: 512` | Hopper's default 1024 produced a 26.16 GiB transient activation peak and zero extensible KV blocks. Reducing only the prefill batch to 4096 still failed. Sequence count 512 boots with the default 8192-token batch and a 14.26 GiB activation peak. |
| DSpark probabilistic drafting + block rejection | Same-venue on/off comparison improved warm single-stream decode from 122.5 to 274.6 tok/s and aggregate C8/C32 throughput from 705/2009 to 1042/2451 tok/s. |
| `mm-encoder-tp-mode: data` | Nine fresh 1024×1024 images took 0.436 s median versus 0.496 s with default weight parallelism. One image was slightly slower: 0.152 versus 0.142 s. |

Removed explicit FP8 KV dtype and DSpark width: this checkpoint/backend resolves
`auto` to `fp8_ds_mla` and derives five draft tokens from `dspark_block_size`.
The final launch verified both defaults. Tokenizer mode and Engram CPU offload
are also detected/defaulted upstream. Default dtype, executor, prefix caching,
chunked prefill and processor cache settings are omitted. No legacy runner or
collective workaround, expert-parallel override, fixed KV budget, context cap,
or image-count cap is present.

Extensible KV is local to one engine. It does not coordinate multiple processes
sharing GPUs. The test used a dedicated engine; shared deployments still need
explicit memory budgets and their own qualification. Its startup estimate of
8.23 full-window contexts is an estimate, not a measured concurrency guarantee.

## Correctness and performance

The certified launch inspected 102 constrained outputs from 100
requests with zero corrupt openers; response shapes were `{'constrained': 100}`.
B4 returned HTTP 200. Automatic tool arguments matched exactly, and reasoning
was nonempty with the correct final answer. Natural DSpark acceptance was
0.391 over the measured interval.

The final full-window request used **1,047,474 input tokens** under
the native **1,048,576-token** window and retrieved the hidden code
in **40.3 seconds**. One and nine images passed.

| warm configuration | single-stream tok/s | C8 tok/s | C32 tok/s | TTFT median (s) |
| --- | ---: | ---: | ---: | ---: |
| DSpark on, explicit KV default | 274.6 | 1042 | 2451 | 0.081 |
| same config, DSpark off | 122.5 | 705 | 2009 | 0.067 |
| automatic KV, default vision weights | 274.4 | 1059 | 2442 | 0.083 |
| automatic KV, data-parallel vision | 255.9 | 1061 | 2442 | 0.078 |

These are medians of three warm rounds. The shipped configuration additionally
omits the checkpoint-derived DSpark width; its fresh launch passed the complete
live gate and supplementary checks. Short-prompt TTFT favors speculation off,
while decode and aggregate throughput favor keeping it.

The vision probe uses distinct solid-color images, neutral position labels,
and a constrained output cardinality. The initial unnumbered nine-image request
was accepted but omitted one repeated color in its answer. Numbered inputs and
a required nine-element response passed; this is a serving/correctness fixture,
not a broad visual reasoning benchmark. No server image limit was introduced.

The long-context code appears only at the beginning of the input, never in the
final question. `/tokenize` counts must agree with inference usage. Two further
requests with distinct codes were submitted concurrently and both retrieved
correctly from 1,047,478 input tokens; their elapsed times were 42.4 and 78.5 s.
Prefill queued, so these do not prove simultaneous full-window decode.

The controlled performance runs used one warmup and three measured rounds on
the same rental, a fresh leading nonce per probe, eight rotating topics within
bursts, fresh image UUIDs, fixed 256-token ignore-EOS decoding, and engine-token
counters. These short synthetic workloads do not establish production latency
percentiles, task quality, or a cross-release regression comparison.

## Validation and resource accounting

The real candidate parser accepted the final YAML. CPU preflight printed
`PREFLIGHT GREEN` with 602 passed and 10 skipped; alignment and pre-commit checks
passed. Candidate CI ran the corrected CPU parser and empty-patch checks.

One watched development rental retained the complete 510,310,568,472-byte
checkpoint and compiler caches through every configuration change. A staging
resume reused 307,237,490,896 bytes and fetched the remaining 203,073,077,576
bytes. The preceding venue went offline before inference and was destroyed;
its full-rate elapsed compute/storage bound was $10.42, excluding unmeasured
transfer. The successful venue costs $19.78/hour plus $0.0390625/GB inbound.
Full-rate wall-clock accounting overstates compute when the provider pauses
an instance. Image-pull transfer is outside container network counters.

The final container memory limit was 1,101,607,731,200 bytes; its observed
cgroup peak was 316,492,111,872 bytes at collection. These include host-side
checkpoint/cache effects. [Publication, cost bounds and verified cleanup](20261117-cleanup.md) are
recorded separately from inference results; raw rental identities remain private.
