# v0.34.0 — H200 tuning and host KV reuse

The selected profile adds adaptive DSpark verification and a 256 GiB native
CPU KV tier. Prompt usage details, native context, vision, tools, and reasoning
remain enabled. No image cap, context reduction, or new admission limit was added.

## CPU cache proof

Three distinct 132k-token prompts placed a secret only at the beginning. Each
ran cold, as a GPU cache hit, and after successful GPU-only cache reset.
Answers and real tokenizer/inference token counts were checked.

All three CPU reloads reused **131,968 tokens** and loaded **964,422,144 bytes**
from CPU to GPU across the workers. GPU prefix-hit counters were zero for
those reloads; external prefix-hit counters increased. Median elapsed time
was **3.030 s cold**, **0.403 s GPU hit**, and **0.405 s CPU reload**. The control
without a CPU tier returned zero cached tokens after reset and recomputed
the prompt in about 3 seconds.

This proves reuse after explicit GPU-cache eviction with DSpark and packed
FP8 KV. It does not stress-fill the full host tier or establish production
eviction rates. Development endpoints were enabled only on loopback for the
cache-reset probes; the deployment YAML needs no development-mode setting.

## Recipe review and staging

The [current upstream recipe](https://github.com/vllm-project/vllm/blob/8f3c672dc02b2f0804cb96ebe4611835715bb193/recipes/models/deepseek-ai/DeepSeek-V4.1-Flash.yaml)
was checked against the v0.34.0 parser and source. DeepInfer's
[published framework](https://github.com/deepseek-ai/DeepInfer/tree/a679bb86ce36e883a98a97733492b686e5b9a08e)
lists NVIDIA SM100 support. In this release, DeepSeek FlashInfer sparse
attention targets SM100/SM120 families, MegaAttention and DeepSelect target
Blackwell, and `latency_specialized` requires SM103. Those presets were
excluded before paid inference instead of forced onto Hopper.

All 66 selected checkpoint files, **510,310,568,472 bytes**, were staged on
CPU-only compute before GPU allocation. Weight SHA-256 values matched pinned
Hub metadata. Download completion took **1783.6 s**, and verification took
**712.4 s**. The runtime used `HF_HUB_OFFLINE=1`. Initial model loading took
about 553 s; a later cached load took about 64 s.

One brief setup allocation ended because an optional topology query was
treated as fatal. It was made nonfatal before the measured session. External
app watchdogs and native timeouts bounded compute. Configuration changes kept
the development container and checkpoint cache warm. Native CPU KV allocation
used slower per-page initialization because the venue did not implement
`MADV_POPULATE_WRITE`.
