# v0.28.0 — 2026-09-01 DeepSeek-V4 DSpark validation (off-gate)

An off-gate session on two rented 2xH200 SXM slices of vast machine 131918
(offer 39604999, instances 49507759 and 49513987, `gpu_frac 0.25` 2-of-8 slices,
driver 580.159.03, CUDA 13.0, torch 2.13.0+cu130) running
`openimage/vllm-openai-audio:v0.28.0`. It measured DSpark against the spec-off
[`deepseek-v4-tp2-h200.yaml`](../engine/deepseek-v4-tp2-h200.yaml) this release
directory shipped, and produced
[`deepseek-v4-tp2-h200-dspark.yaml`](../engine/deepseek-v4-tp2-h200-dspark.yaml).
**The scope of that validation: an NVLink 2xH200 slice at concurrency 1–8 only;
unmeasured above 8, where the pool admits ~35 streams of 131K-token requests. A
16/32/64 sweep on the dedicated PCIe box is required before either file is used
for production traffic.** Box 1 ran 58 min 09 s for ~$7.84 and box 2 ran 59 min 00 s for ~$7.97, both at
$8.094/hr — an agent-reported session total of ~$16.69, of which GPU time is
$7.84 + $7.97 = $15.81 and the remaining ~$0.88 is egress and storage.
Destruction has two independent confirmations, both reading
`vastai show instances-v1` as `Total: 0 instances`: the running agent's own
audit after box 2, and a later re-audit by the coordinating session.

**Venue caveat — this is not the production topology.** No non-NVLink 2xH200
offer was rentable, so both slices were NVLink pairs (`nvidia-smi topo -m`
reports NV18, and all-reduce resolved to `['CUSTOM','SYMM_MEM','PYNCCL']`).
Production is PCIe H200 without NVLink. Boot, correctness, batch-1 latency,
concurrency 1–8 and crash probing are covered; the TP2 all-reduce bug class
that needs a link-free pair is **not** exercised by any number below.

**Concurrency caveat — 8 is not the ceiling.** The shipped configuration boots
with a KV pool that works out to about 35 concurrent 131K-token streams (derived
from the boot pool size below, not a measured line), and nothing here measures
DSpark above concurrency 8. Speculative decoding is the shape that
degrades as a batch fills — the fork has a measured Gemma MTP collapse on
exactly that axis — so the concurrency-8 numbers are the top of what this
session can support, not a statement about a full engine. **Open item alongside
the venue: sweep concurrency 16 / 32 / 64 on the dedicated box.**

## Measured configurations

Every arm below ran default cudagraph on one box, with the baseline anchored on
that same box. `tok/s` at concurrency 1 / 2 / 4 / 8.

| arm | indexer | conc1 | conc2 | conc4 | conc8 | acceptance | acc. len (conc8) |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| baseline (no spec) | next_n=1 native | 137.3 | 251.1 | 432.4 | 694.8 | — | — |
| **DSpark k=3 (shipped)** | **next_n=4 native** | **252.5** | **398.0** | **624.9** | **930.2** | 0.47–0.51 | 1.41 |
| DSpark k=4 | next_n=5 flattened | 268.5 | 383.9 | 607.2 | 894.2 | 0.39–0.48 | 1.54 |
| DSpark k=5 | next_n=6 flattened | 256.6 | 368.3 | 590.7 | 856.1 | 0.31–0.37 | 1.62 |

DSpark beat the baseline at every concurrency this session measured — 1, 2, 4
and 8 — and nothing here measures above 8.
k=3 is +59% / +45% / +34% over baseline at concurrency 2 / 4 / 8, and every arm
booted with `DSpark draft model loaded: 97 params` and captured cleanly — no
trace of the v0.27.1 DeepGEMM SM90 crash, and neither of the two failures
source review predicted (an FA3 `scheduler_metadata` mismatch, a PIECEWISE
capture failure). The concurrency-2 crash probe that historically killed DSpark
was run 10x across the spec arms with zero crashes.

**Why k=3 and not more.** `indexer.py:553` sets `next_n = k + 1`, and SM90's
native paged-MQA decode kernel accepts only `next_n in (1, 2, 4)`
(`utils/deep_gemm.py:555-563`); above that the indexer flattens to one row per
query and re-reads the KV tile per row. k=3 is therefore the only k >= 2 that
stays native, and the k=3 -> k=4 boundary is exactly where throughput reverses.
The mechanism isolates cleanly rather than being an acceptance artifact: mean
accepted length *rises* with k (1.41 / 1.54 / 1.62 at concurrency 8) while
throughput *falls*, so k=4 accepts more tokens per step and is still slower.
Per-position acceptance measured at k=7 says the same thing from the other side
(8,893 drafts, 61,085 drafted tokens, 15,344 accepted):

| position | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| accepted | 6196 | 3960 | 2337 | 1391 | 770 | 445 | 245 |
| rate | 69.7% | 44.5% | 26.3% | 15.6% | 8.7% | 5.0% | 2.8% |

Positions 5 and 6 cost a full draft slot each and return almost nothing — a
first-principles argument for a small k, independent of the indexer shape.

**Batch 1 is not a k discriminator.** A concurrency-1 level is only two
requests; k=3 measured 252.5 and 285.4 across two runs against k=4's 268.5 and
k=5's 256.6. The defensible statement is ~1.85–1.95x baseline for any k in 3–5
(per-token 3.5–3.8 ms against 7.17 ms). The k ordering above rests on
concurrency 2 / 4 / 8, where each point is 4 to 16 requests.

## PIECEWISE against the engine default

Measured on the other box, `tok/s` at concurrency 1 / 2 / 4 / 8:

| arm | conc1 | conc2 | conc4 | conc8 |
| --- | ---: | ---: | ---: | ---: |
| baseline, `cudagraph_mode: PIECEWISE` | 131.5 | 241.4 | 432.9 | 678.4 |
| baseline, engine default | 136.9 | 250.7 | 430.6 | 669.6 |
| DSpark k=5, `cudagraph_mode: PIECEWISE` | 189.8 | 357.2 | 575.6 | 872.2 |
| **DSpark k=5, engine default** | **261.0** | **369.8** | **597.5** | **909.4** |

PIECEWISE is neutral for the baseline (+-4%) and costs DSpark **27% at batch 1**
and 4% at concurrency 8. Under PIECEWISE the draft never gets a FULL cudagraph
and runs eager (`gpu/spec_decode/dflash/speculator.py:113-129`). It is also no
longer protective: the flag was added on v0.27.1 to dodge a DeepGEMM SM90
out-of-bounds read that the v0.28.0 repin onto `deepseek-ai/DeepGEMM@8b1392b9`
fixes with a `q_idx` clamp and an empty-schedule guard, and under Model Runner
V2 the DSV4 attention layer picks its own eager region
(`models/deepseek_v4/attention.py:302-307`). The default `FULL_AND_PIECEWISE`
booted and captured on every arm.

The frozen file's header claims the DeepGEMM bug is "still open upstream
(deepseek-ai/DeepGEMM#399)", which reads an open PR as an unfixed bug. The
tracker states, precisely: **DeepGEMM#399 is open and unmerged**, superseded by
the v0.28.0 repin, which reached the same clamp by another route;
**vllm#51182 is closed unmerged**, likewise superseded by the repin;
**vllm#51181 is closed via vLLM-side capture changes**, not via the repin; and
**vllm#51318 is merged and in this tag**. An open PR number is not evidence
that the defect ships.

Cross-box sanity: baseline 136.9 / 669.6 against 137.3 / 694.8, and k=5
261.0 / 909.4 against 256.6 / 856.1 — the two boxes agree within 1–6%.

## Structured output

8 requests per arm, `response_format: json_schema` with four required keys
(three string, one integer), `strict: true`. **0 of 8 failures in each of nine
arms**, with no parse errors, no missing keys and no type violations. The
coverage is uneven and worth naming: baseline and DSpark k=5 were probed in
both cudagraph modes; k=3 and k=4 in default mode only; k=7 under PIECEWISE
only. DSpark does not corrupt guided output the way
Gemma's MTP path did. This rules out gross corruption, not a rare defect: 0 of
8 has a Wilson upper bound near 32%.

## Operational caveats

1. **An intermittent engine stall, cause unresolved.** Four occurrences: three
   at concurrency 8 (20.8 / 24.6 / 27.5 s) and one at concurrency 4 (2.0 s). A
   stream went silent mid-generation while the engine's own log reported
   `Avg generation throughput: 0.0 tokens/s, Running: 8 reqs` with 99% of the
   KV cache free, then recovered with no error. Observed on baseline and spec
   arms alike. Warm back-to-back repeats at concurrency 8 — 8 runs on baseline
   and 6 on k=5, nothing else changed — were clean 8/8 and 6/6. Both boxes were
   2-of-8-GPU slices of a shared host, so a noisy neighbour and an engine bug
   cannot be separated on this venue. **Open item: re-check on the dedicated
   PCIe box.** No reported number is contaminated; every affected level was
   re-run clean.
2. **The draft costs KV pool.** The k=3 boot receipt, verbatim:
   `kv_cache_utils.py:1869 GPU KV cache size: 4,590,462 tokens, Maximum
   concurrency for 1,048,576 tokens per request: 4.38x`, against the baseline's
   `5,210,482 tokens ... 4.97x`. Both multiples are quoted at the model's full
   1,048,576-token `max_position_embeddings` because no arm set
   `max-model-len`; **no 131,072-capped line was measured.** Derived from those
   pool sizes, a 131,072-token request gives ~35.0 concurrent streams with the
   draft against ~39.7 without — the draft costs about 12% of the pool. The k=3
   cudagraph capture size was not recorded; the only measured capture delta is
   k=5, at 3.19 GiB against the baseline's 2.96 GiB.
3. **Never set `VLLM_USE_V2_MODEL_RUNNER=0`.** `method: dspark` force-selects
   Model Runner V2 (`config/vllm.py:624-632`) because DSpark exists only in the
   V2 tree; forcing V1 routes it into the still-open vllm#50851.
4. **Do not add `enable_adaptive_verification`** — it raises at startup on SM90
   (`adaptive_verification.py:453-470`), and the PR that would enable it is not
   in this tag. **Do not add `indexer_kv_dtype: mxfp4`** (raises below sm_10x),
   and do not expect a dynamic speculative schedule to do anything: nothing in
   the V2 tree reads it, so it silently desynchronizes the scheduler budget
   instead of turning speculation off above batch 1.
5. **The one-line regression check after any k change.** Grep the boot log for
   `indexer.py:558 DSA indexer decode path: use_flattening=False
   supports_varlen=False (next_n=4, use_fp4_cache=False)` — that line is the
   whole native-against-flattened discriminator, and it is what silently
   regresses if someone bumps k.
