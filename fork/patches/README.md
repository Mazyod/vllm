# Fork patches — filing and context

This directory is the generated form of the fork's release commits. Every patch
commit records enough detail to answer, months later: what bug is this, why does
it hurt us, why does the fix work, how do I reproduce it, and when do we drop it.

> **Public repository.** Commit messages are public. Never include private,
> confidential, or personally identifiable information — no customer/organization
> names, no internal hostnames, tokens, IPs, credentials, private URLs, or people.
> Keep model names, hardware classes (e.g. SM90/H100), commands, and upstream
> issue/PR links; those are what make a note useful and are safe to publish.

## Layout

```text
fork/patches/
├── README.md                 # this file — contract + retirement record
├── RELEASE                   # pinned tag and exact export commit
├── series                    # generated apply order
├── upstream.map              # generated Upstream-Merge value for every patch
└── 000N-<slug>.patch         # one generated diff per patch commit
```

`README.md` is the only hand-written file in this directory. Every other file
is generated by
`../scripts/export-patches.sh`; do not edit them by hand. The `.patch` files and
`series` are consumed by `../docker/apply-patches.sh`. Operational mechanics
live in the top-level [`FORK.md`](../../FORK.md).

## Adding a patch

A patch is the fork's most expensive kind of divergence, so it has to clear the
charter's bar first (FORK.md § Charter):

- **One goal, traceable upstream.** Exactly one upstream PR, or one
  narrowly-stated fork need — never a bundle. If you cannot name the single
  thing it fixes, it is not ready.
- **Smallest possible diff.** Only the files that goal requires. No drive-by
  edits, no local "improvements" to vLLM, no test files that the runtime image
  does not carry.
- **A stated exit.** Record the upstream commit that will retire it, so the next
  release can drop it mechanically. A patch with no exit criterion does not go in.

Create one commit on `release/<tag>` with this template:

```text
[fork-patch] <short description>

Impact: <symptom, blast radius, error text, and frequency>
Root cause: <mechanism and why the fix works>
Reproduce: <portable steps and expected stock/patched behavior>
Validation: <what was tested, on what hardware, and when>
Ruled out: <dead-end hypotheses worth preserving>

Upstream-PR: https://github.com/vllm-project/vllm/pull/NNNNN
Upstream-Merge: <40-hex merge SHA, or none>
Exit-Criterion: <condition under which this patch is dropped>
```

All five section headings must start a line. Their order is not significant.
`Upstream-PR` must start with
`https://github.com/vllm-project/vllm/pull/`.

Then run `fork/scripts/export-patches.sh <release-sha>`. The history checker
rejects missing trailers, merge or empty commits, paths outside `vllm/**`, and
changes GNU `patch` cannot represent safely.
